## 开发顺序与提前约束

以下保留模块拆分时的依赖与约束，用于理解设计取舍。实际下一步以本页的 [当前接续点](#当前接续点) 为准。

默认顺序为 M1 → M2 → M3 → M4 → M5 → M6。先设计 M1，但同时检查 M4、M5 对数据的要求：消息所属成员、轮次与候选版本、知情记录、各成员继承边界和状态恢复依据必须能够表达，避免后面反复迁移。提前检查契约不意味着提前实现全部功能。

M1 完成最小创建和读取入口，M2 能展示一条带明确角色身份的发言，M3 能观察完整互动。指定角色生成仅为 M2 的内部验证能力，不增加用户手动调度需求。

优先用 M2–M3 的小型原型验证秘密隔离、旁听沉默和 A → B → A。质量不达标时先调整核心机制，不急于铺开全部界面。真实模型验证遵守独立配置与数据要求，模拟调度通过不能宣称模型判断准确。

M5 持续形成群聊长期记忆是正式首版要求，不是可删减的附加项。M4 完成前的演示版不得宣称支持可靠的候选切换与恢复。

## 每批交付与接续

每批遵循“读取当前状态 → 设计或实现一个明确范围 → 执行对应检查 → 更新记录”。共享基础设施、迁移和跨端改动的验证范围遵循根协作约定，不因模块拆小而省略必要检查。

批次记录写入对应模块设计、验收报告或 [交接历史](HISTORY.md)，并注明日期与版本；至少包含变更范围、涉及文件或提交、实际检查与结果、剩余问题及下一步。完成状态必须附可核对的证据；失败和未执行的检查如实写明。真实模型与真机验收单独列出，不将测试日志中的敏感内容或真实个人数据写入仓库。

新聊天接续时先读总规划与本页，再读当前模块设计和相关实现。无需从聊天历史重新推断需求，也不依赖另一个泛化项目状态文档来判断群聊是否完成。
