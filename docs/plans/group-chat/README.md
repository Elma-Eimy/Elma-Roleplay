## 开发顺序与提前约束

默认顺序为 M1 → M2 → M3 → M4 → M5 → M6。先设计 M1，但同时检查 M4、M5 对数据的要求：消息所属成员、轮次与候选版本、知情记录、各成员继承边界和状态恢复依据必须能够表达，避免后面反复迁移。提前检查契约不意味着提前实现全部功能。

M1 完成最小创建和读取入口，M2 能展示一条带明确角色身份的发言，M3 能观察完整互动。指定角色生成仅为 M2 的内部验证能力，不增加用户手动调度需求。

优先用 M2–M3 的小型原型验证秘密隔离、旁听沉默和 A → B → A。质量不达标时先调整核心机制，不急于铺开全部界面。真实模型验证遵守独立配置与数据要求，模拟调度通过不能宣称模型判断准确。

M5 持续形成群聊长期记忆是正式首版要求，不是可删减的附加项。M4 完成前的演示版不得宣称支持可靠的候选切换与恢复。

## 每批交付与接续

每批遵循“读取当前状态 → 设计或实现一个明确范围 → 执行对应检查 → 更新记录”。共享基础设施、迁移和跨端改动的验证范围遵循根协作约定，不因模块拆小而省略必要检查。

批次记录至少包含变更范围、涉及文件或提交、实际检查与结果、剩余问题及下一步。完成状态必须附可核对的证据；失败和未执行的检查如实写明。真实模型与真机验收单独列出，不将测试日志中的敏感内容或真实个人数据写入仓库。

新聊天接续时先读总规划与本页，再读当前模块设计和相关实现。无需从聊天历史重新推断需求，也不依赖另一个泛化项目状态文档来判断群聊是否完成。

## 当前接续点

M1-A 已实现会话类型、多 Persona 关系、成员位置约束、旧入口类型检查与角色删除保护。临时库已验证迁移保留旧引用、故障整体回滚和含群聊时拒绝降级；详细证据与旧入口清单见 [M1 接续记录](M1_DATA_AND_PERSONAS.md#接续记录)。

M1-B 已实现原子创建、来源状态与有效记忆快照、列表详情和完整删除，包含来源修改竞争、角色删除竞争和取消时锁释放的隔离回归。快照表通过独立迁移加入，继承内容不进入单聊 MemoryChunk 或向量索引。

M1-C 已接通群聊 HTTP 访问策略、请求模型、[领域 API 契约](../../api/GROUP_SESSIONS.md)、前端类型与 Mock。群聊目标和单聊来源分别校验；Mock 原卡起步可用，单聊快照明确不支持。

下一项工作是 M1-D：最小群聊创建、列表与详情页面，防重复提交、切服/离页的迟到响应隔离及手工流程验收。当前可通过 API 创建和管理群聊，没有页面入口、发送或生成接口；未执行真实模型或真机验收。
