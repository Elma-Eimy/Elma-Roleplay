# 群聊问题清单与返工要求

[实施入口](README.md) · [需求基线](REQUIREMENTS.md) · [历史验证记录](../../testing/group-chat/README.md)

记录日期：2026-11-11。来源为用户实际移动端使用反馈。本清单五项均未解决，群聊整体未通过验收。之前的构建、自动回归和有限真实 API 成功不能覆盖这些反馈，也不能作为关闭问题的理由。

后续方向已由用户调整：先完成普通共同群聊，冻结裁决与私密空间能力；角色复用单聊 XML 与提示词组装，导演只负责顺序和条数。原文中的“裁决负责知情”暂缓，不据此继续扩展协议。本地返工进行中，尚未作真实模型或移动端通过结论。

首次登记时只记录问题，未修改业务代码、调用模型或部署。后续用户已授权本地返工与真实场景验证，仍不部署。接续先读本清单；与旧阶段规划冲突的处理方向以用户最新要求为准。

## 1. 角色输出复用单聊协议

- [ ] 移除角色生成阶段额外的群聊 JSON 输出要求，复用已有单聊输出协议。

用户已多次遇到无法完成回复，明确否定当前角色生成 JSON 分段、字段对齐及格式修补这一套设计。不能继续把新增协议及校正调用当作默认修复方向。

角色负责正常生成回复；裁决模型负责判断回复能够被哪些成员看见。不得要求角色模型同时承担裁决职责。内部持久化需要的结构与模型必须输出的协议应分开；已有群聊数据的读取兼容不能以清库解决。

验证必须使用实际角色卡、示例、模型与思考配置，核对角色请求确实使用单聊协议，而非仅检查几份手写 JSON 可以解析。

## 2. 一个角色生成完毕就展示

- [ ] 按角色增量交付和展示，不等待整轮所有角色生成或审核结束。

用户否定“一轮整体输出”的交互。应记录每个角色生成结束与移动端实际显示的时间，确认后续角色仍在处理时，前一个角色的完整回复已经能看见。

后续角色失败不能吞掉或重放已经展示的回复。逐条展示、保存、裁决与断线恢复的关系需要检查清楚；候选和轮次是内部组织方式，不能成为等待整轮完成才显示的理由。

## 3. 生成与审核耗时过长

- [ ] 缩短用户等待时间，检查串行生成、裁决、额外审核和格式修补的累计成本。

用户实际体验需要等待约两分钟且仍可能失败，无法接受。此前本地完整回放约101秒和91秒，只证明当时可以完成，不能当作性能通过。

后续应分别记录首条回复可见时间、每个角色生成耗时、裁决耗时、审核与重试调用次数，以及整次互动耗时。不能仅通过放大 token 额度、超时或重试上限掩盖问题。正常角色扮演不应因模糊审查反复重写。

## 4. 发言上限不应成为生硬的剧情停止

- [ ] 重新处理“已达到发言上限，互动已经停止”等终止行为和提示。

用户明确反对该表现。技术执行预算不等于人物自然结束互动，也不能用“操作已完成”掩盖无有效回应或过早结束。

需要分别检查自然等待用户、后台预算暂停、实际生成失败的含义和移动端表现。是否提供继续及如何接续应与用户交互保持一致，不能只改一句文案就认定解决，也不能直接删除所有后台资源边界。

## 5. 移动端群聊界面仍不合格

- [ ] 重新检查实际移动端界面与完整使用流程，不能将已有组件抽取或 H5 截图当作完成。

用户明确反馈当前前端仍然很差。继续以其已有单聊界面为复用基线，检查气泡、立绘和代入感、抽屉管理、头像角色详情与提示词入口、模型选择、键盘弹出及输入框高度变化，以及逐角色回复和错误状态的展示。

此处记录检查范围，不表示这些入口全部缺失；具体缺陷以真实界面核对。客户端是移动端，服务器部署范围为后端，不自行安排前端网站部署。

## 后续验证和交付约束

优先使用用户实际失败场景和真实角色卡，固定源码、模型、思考强度与输入，保留失败和重复运行结果。自己生成的简单样本可以作为回归补充，不能成为主要可用性证据；真实 API 调用次数多也不等于场景覆盖充分。

在本地启动后端完成调试，不在服务器临时目录反复改代码和试跑。服务器只在明确授权的部署或必要只读取证范围内操作。不得将用户新失败未经查证一概归因于 JSON，也不得把接口成功、轮次结束与有效回复混为一谈。

后续逐项记录实际改动、验证证据和剩余问题。在这些问题解决前，不再将群聊描述为“已验收”或要求用户配合深夜验收。此次记录没有解决上述任何一项。
