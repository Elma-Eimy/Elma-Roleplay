## 待修复与扩大验收

### 输出协议仍会失败

本次四次操作因 `invalid_output` 失败：三个角色响应缺少必填 `status`，另一个 JSON 在 `units` 数组中提前闭合对象。JSON 模式不能保证必填字段或完整结构。服务端拒绝无效输出，保留候选状态，未把残缺发言当作成功提交；需要显式续接时会再次产生费用。成长复测通过一次显式 resume 完成，不是首遍无故障通过，也没有自动重发原聊天 POST。

后续优先验证角色生成协议的稳定性，并补未参与调试的新场景。不能通过接受缺字段、静默补状态或放宽 JSON 校验来消除测试失败。

### 明确更正没有形成覆盖关系

旧快照是“铜铃原定交给编号 Q17 的青鹭”，私聊明确取消并改交赤羽。提纯获得了相关旧卡编号，但新卡写成包含确认与保密承诺的 `event`，没有返回 `replaces_id`。后续本人 Prompt 同时出现新群内卡与旧快照，角色回答采用了赤羽，没有误答旧安排；这不能算旧事实覆盖验收通过。

当前程序对已给出的覆盖引用做归属与时序校验，是否生成引用仍取决于模型。后续需要针对明确修正提高覆盖召回，同时保留“不因话题接近而误覆盖”的反例。

### 对用户印象没有完整提取

记录员亲口承认偷铃并栽赃岑夏。岑夏的提纯输入中已有这条用户台词，允许 `target=user`；模型却引用岑夏自己的回应生成对用户印象。校验拒绝后，纠正响应删除该印象，最终只保存对陆遥的定向印象。陆遥的首次结果另使用非法记忆类型 `action`，纠正响应删去后写入有效卡。

证据约束起到了拒绝错误来源的作用，但“有重要经历就稳定形成相应关系变化”尚未达标。需要分别核对提取召回率与引文归属，不能把过滤后任务完成当作内容完整。

### 混合事实与请求的分类仍有损失

私聊输入将“取消旧安排、改交赤羽、私密编号”和“请确认”放在同一连续片段。初判把该片段整体归为 `request`，因此用户原话没有进入长期提纯证据；新安排最终依靠岑夏复述才被保存。若角色没有复述，可能漏掉长期事实。本次只观察到这一处，不据此推断普遍漏记率。

后续应使用“事实陈述 + 执行请求”的混合样本验证分段，并保留单纯推进请求不入长期事实的反例。
